# Laboratorios 10–13: procesamiento, observabilidad y seguridad de Kafka

Guía unificada para trabajar con datos sintéticos. Cada laboratorio tiene cuatro pasos; cada paso declara qué hacer, qué resultado observar y qué concepto explicar. No use datos reales de contribuyentes.

## Mapa del entorno Compose

El Compose base contiene los tres brokers Kafka en KRaft y Kafka UI. Los archivos de etapa se combinan con el base solo cuando el laboratorio lo requiere:

```bash
# Etapas A/B: brokers y Kafka UI
docker compose -f docker-compose-lab-kafka.yml up -d

# Etapa C: Schema Registry, Connect y PostgreSQL
docker compose -f docker-compose-lab-kafka.yml \
  -f docker-compose.etapaC.yml up -d

# Etapa D: exporters JMX y de consumer lag
docker compose -f docker-compose-lab-kafka.yml \
  -f docker-compose.etapaD.yml \
  up -d broker1 broker2 broker3 kafka-exporter

# Servicios de C y exporters de D juntos
docker compose -f docker-compose-lab-kafka.yml \
  -f docker-compose.etapaC.yml \
  -f docker-compose.etapaD.yml \
  up -d broker1 broker2 broker3 schema-registry connect postgres kafka-exporter
```

No ejecutes `docker compose -f docker-compose.etapaD.yml up -d` por separado: D es un **overlay**, no un Compose autónomo. Por eso `broker2` no tiene `image` ni `build` hasta combinarlo con el archivo base. El comando de arriba combina ambos archivos y levanta solo los servicios Docker solicitados. Prometheus y Grafana ya están instalados directamente en la máquina; no son contenedores de este Compose y no se deben levantar con Docker. Prometheus: [http://35.170.6.137:9090/](http://35.170.6.137:9090/). Grafana: [http://35.170.6.137:3000/login](http://35.170.6.137:3000/login). La guía no almacena la contraseña; usa la credencial configurada en Grafana. MinIO también es externo; el Compose de Etapa C no debe declarar un servicio MinIO. PostgreSQL sí es un contenedor de Etapa C.

Kafka UI escucha en el puerto `8080` del contenedor y se publica en `8085` del host: `http://<host>:8085`. Si el archivo Compose todavía contiene `ports: ["8081:8080"]`, cambie esa publicación a `ports: ["8085:8080"]`; el puerto `8081` queda para Schema Registry. Desde el host, los listeners externos de Kafka son `localhost:9092`, `localhost:9094` y `localhost:9096`. Desde otros contenedores de Compose, use `broker1:19092,broker2:19092,broker3:19092`.

En Etapa D, los exporters JMX se publican en los puertos `9101–9103` y el exporter de lag en `9308`. La instancia externa de Prometheus debe poder alcanzar `35.170.6.137:9101–9103` y `35.170.6.137:9308` (si esa IP corresponde al host Docker y las reglas de red permiten esos puertos); no configure `KAFKA_JMX_PORT` allí: son endpoints HTTP, no RMI. No uses `localhost` en los targets de Prometheus salvo que Prometheus corra en el mismo host que los exporters.

Desde el Laboratorio 12, la práctica de seguridad usa únicamente `docker-compose.etapaE.yml`, con un broker para TLS/SCRAM/ACL. No la combines con base, C o D. Demuestra controles de seguridad, no replicación ni alta disponibilidad. Detén las etapas anteriores con `down` sin `-v`; `down -v` elimina volúmenes y datos.

## Laboratorio 10 — Agregación por NIT con Kafka y Python estándar

**Objetivo:** consumir eventos de Kafka y observar conteo, suma por hora y efecto de la gracia. No instala librerías ni crea archivos de código. Esta demo no es Kafka Streams y no demuestra topics internos ni restauración automática.

### Paso 1 — Crear un topic de prueba y enviar cuatro facturas

Desde la raíz del repositorio, cree un topic aislado y publique datos reproducibles:

```bash
cd ~/kafka-dian
docker exec broker1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server broker1:19092 --create --if-not-exists \
  --topic lab10.facturas --partitions 1 --replication-factor 3 \
  --config min.insync.replicas=2

printf '%s\n' \
  '{"nit":"900123456","valor":100,"timestamp_evento":"2026-11-20T12:10:00Z"}' \
  '{"nit":"900123456","valor":50,"timestamp_evento":"2026-11-20T12:20:00Z"}' \
  '{"nit":"900123456","valor":75,"timestamp_evento":"2026-11-20T10:30:00Z"}' \
  '{"nit":"900123456","valor":25,"timestamp_evento":"2026-11-20T10:40:00Z"}' | \
docker exec -i broker1 /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server broker1:19092 --topic lab10.facturas
```

**Resultado:** Kafka confirma que las cuatro líneas se publicaron en `lab10.facturas`.

### Paso 2 — Contar y sumar con diez minutos de gracia

El consumidor de consola envía los cuatro JSON a Python, que usa solo módulos incluidos con Python 3:

```bash
docker exec broker1 /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server broker1:19092 --topic lab10.facturas \
  --from-beginning --max-messages 4 | GRACIA_MINUTOS=10 python3 -c '
import json, os, sys
from collections import defaultdict
from datetime import datetime, timezone
from decimal import Decimal

hour_ms = 3600000
grace_ms = int(os.environ["GRACIA_MINUTOS"]) * 60000
watermark = None
totals = defaultdict(lambda: [0, Decimal("0")])
for line in sys.stdin:
    event = json.loads(line, parse_float=Decimal)
    timestamp = datetime.fromisoformat(event["timestamp_evento"].replace("Z", "+00:00"))
    event_ms = int(timestamp.timestamp() * 1000)
    watermark = event_ms if watermark is None else max(watermark, event_ms)
    start = event_ms // hour_ms * hour_ms
    end = start + hour_ms
    if watermark > end + grace_ms:
        print("TARDIO: enviar a revisión", event)
        continue
    key = (event["nit"], start)
    totals[key][0] += 1
    totals[key][1] += Decimal(str(event["valor"]))
    inicio = datetime.fromtimestamp(start / 1000, timezone.utc).isoformat()
    print("AGREGADO", key[0], inicio, "conteo=", totals[key][0], "valor_total=", totals[key][1])
'
```

**Resultado:** las dos facturas de las 12:00 suman `conteo=2`, `valor_total=150`; las de las 10:00 se identifican como tardías.

### Paso 3 — Repetir con más gracia

Repite el comando del Paso 2 cambiando `GRACIA_MINUTOS=10` por `GRACIA_MINUTOS=120`.

**Resultado:** ahora se aceptan también las dos facturas de las 10:00 y su total es `conteo=2`, `valor_total=100`.

### Paso 4 — Explicar el límite de la demo

**Aprendizaje:** la ventana agrupa por hora y el watermark avanza con el timestamp de los eventos. La demo imprime los tardíos para revisión, pero no los persiste y pierde sus totales al cerrar. No es Kafka Streams: no crea changelog/repartition ni restaura estado.

## Laboratorio 11 — Tablero y alertas con Prometheus externo

**Objetivo:** comprobar métricas reales, construir seis paneles y observar lag sin detener brokers en el clúster compartido.

### Paso 1 — Levantar brokers y exporters

Desde la máquina Docker, prepara JMX y levanta base + D. Prometheus y Grafana ya corren como servicios del host; no los subas con Compose:

```bash
cd /home/est1/equipo01/kafka-dian/entorno
mkdir -p jmx
wget -O jmx/jmx_prometheus_javaagent-1.6.0.jar \
  https://github.com/prometheus/jmx_exporter/releases/download/1.6.0/jmx_prometheus_javaagent-1.6.0.jar
chmod 755 jmx
chmod 644 jmx/kafka.yml jmx/jmx_prometheus_javaagent-1.6.0.jar

docker compose --project-directory /home/est1/equipo01/kafka-dian/entorno \
  -f /home/est1/equipo01/kafka-dian/entorno/docker-compose-lab-kafka.yml \
  -f /home/est1/equipo01/kafka-dian/entorno/docker-compose.etapaD.yml \
  up -d broker1 broker2 broker3 kafka-exporter

docker exec broker1 /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server broker1:19092 --create --if-not-exists \
  --topic lab11.grafana-demo --partitions 1 --replication-factor 3

printf '%s\n' \
  '{"evento":1,"valor":100}' \
  '{"evento":2,"valor":200}' \
  '{"evento":3,"valor":300}' \
  '{"evento":4,"valor":400}' \
  '{"evento":5,"valor":500}' | \
docker exec -i broker1 /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server broker1:19092 --topic lab11.grafana-demo

docker exec broker1 /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server broker1:19092 --topic lab11.grafana-demo \
  --group grafana-demo --from-beginning --max-messages 1
```

**Resultado:** los brokers y el exporter están arriba; se publica una muestra de cinco eventos y el grupo `grafana-demo` consume uno, dejando lag para visualizar. No combines D con los contenedores externos de Prometheus/Grafana ni detengas consumidores compartidos.

### Paso 2 — Confirmar la conexión y consultar una métrica

En Prometheus → **Status → Targets**, confirma `kafka-brokers` (3/3 UP) y `kafka-lag` (1/1 UP). En **Graph**, ejecuta:

```promql
sum(kafka_server_replicamanager_underreplicatedpartitions)
```

**Resultado:** `0` significa que no hay particiones sub-replicadas. Si los targets están DOWN, revisa el `prometheus.yml` activo en `/etc/prometheus/prometheus.yml`; los jobs deben apuntar a `127.0.0.1:9101–9103` y `127.0.0.1:9308` si Prometheus y Docker comparten máquina.

### Paso 3 — Conectar Grafana a Prometheus y crear el dashboard

Antes de crear paneles, en Grafana abre **Connections → Data sources** y selecciona la fuente Prometheus existente o pulsa **Add data source → Prometheus**. Como Grafana y Prometheus corren en la misma máquina, configura la URL `http://localhost:9090` y pulsa **Save & test**. Debe confirmar que la conexión funciona. Si están en hosts distintos, usa la URL de Prometheus alcanzable desde el servidor Grafana.

Luego abre **Dashboards → New → New dashboard → Add visualization**. Selecciona la fuente Prometheus, pega la consulta del panel, ejecútala y elige su visualización. Pulsa **Apply** para añadir cada panel; repite para los seis y al final pulsa **Save dashboard**.

| Panel | Consulta PromQL | Visualización |
|---|---|---|
| Particiones sub-replicadas | `sum(kafka_server_replicamanager_underreplicatedpartitions)` | Stat |
| Particiones fuera de línea | `sum(kafka_controller_kafkacontroller_offlinepartitionscount)` | Stat |
| Controlador activo | `sum(kafka_controller_kafkacontroller_activecontrollercount)` | Stat |
| Conteo de topics | `kafka_controller_kafkacontroller_globaltopiccount` | Stat |
| Offset actual por topic y partición | `{__name__=~"kafka_log_log_logendoffset_topic_.*"}` | Serie temporal/Table |
| Lag por grupo | `sum by (consumergroup) (kafka_consumergroup_lag)` | Serie temporal |

La serie de offset sirve para ver actividad por partición; no equivale a mensajes/s. Los contadores de brokers muestran estado del clúster; el topic/offset se activa con los eventos del paso 1 y el panel de lag con el grupo `grafana-demo`. Si un panel indica `No data`, selecciona el rango **Last 15 minutes**, pulsa **Refresh** y prueba su consulta en Prometheus → **Graph**; no confundas una serie sin muestras con valor cero.

### Paso 4 — Ver lag, crear una alerta y observar recuperación

El consumo parcial del paso 1 deja mensajes pendientes en `grafana-demo`. Espera al siguiente scrape de Prometheus y observa el panel de lag. Crea una alerta de Grafana para `sum(kafka_consumergroup_lag) > 0`, duración 1 minuto, severidad warning y acción “revisar consumidor”. Para despejar el lag después de observarla, consume los mensajes restantes del mismo grupo:

```bash
docker exec broker1 /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server broker1:19092 --topic lab11.grafana-demo \
  --group grafana-demo --from-beginning --max-messages 10
```

**Resultado y aprendizaje:** guarda JSON y capturas del lag y de la alerta `FIRING`; un clúster puede estar sano mientras el consumidor está detenido. La alerta de disco requiere un exporter de host, no disponible aquí.

## Laboratorio 12 — Seguridad Kafka en un broker (TLS + SCRAM)

**Objetivo:** demostrar TLS, autenticación SASL/SCRAM y autorización ACL en un entorno sencillo de un broker. Esta configuración es didáctica: **no** demuestra replicación ni alta disponibilidad.

**Archivos:** el Compose didáctico reemplaza `entorno/docker-compose.etapaE.yml`; usa también el `gen-certs.sh` actualizado. Los secretos van en `entorno/secrets/` (sin punto inicial). No combines esta Etapa E con base/C/D.

### Paso 1 — Apagar etapas anteriores y preparar secretos

Desde `entorno`, baja el stack Kafka previo con los mismos archivos Compose que usaste para levantarlo. Si estaban activos base, C y D:

```bash
cd ~/kafka-dian/entorno
docker compose --project-directory /home/est1/equipo01/kafka-dian/entorno \
  -f /home/est1/equipo01/kafka-dian/entorno/docker-compose-lab-kafka.yml \
  -f /home/est1/equipo01/kafka-dian/entorno/docker-compose.etapaC.yml \
  -f /home/est1/equipo01/kafka-dian/entorno/docker-compose.etapaD.yml \
  down
```

Si solo estaban activos algunos overlays, usa los mismos que usaste al iniciarlos. No añadas `-v`: se detienen los servicios pero se conservan sus volúmenes. Prometheus y Grafana del host no se detienen con Compose. Desde aquí en adelante usa solo Etapa E.

Genera o reutiliza un conjunto completo de secretos:

```bash
bash gen-certs.sh ./secrets
```

Si el generador indica que `datae` ya está inicializado, detente y reutiliza sus credenciales existentes; no borres el volumen.

### Paso 2 — Arrancar la variante de un broker

```bash
docker compose -f docker-compose.etapaE.yml config -q
docker compose -f docker-compose.etapaE.yml up -d
docker compose -f docker-compose.etapaE.yml ps
```

**Resultado:** el contenedor `kafka-etapaE` queda `healthy` y `bootstrap-topics` crea `dian.facturacion.emitida` con tres particiones y factor de réplica uno.

### Paso 3 — Verificar TLS y autenticación correcta

```bash
openssl s_client -connect localhost:9093 -servername broker1 \
  -CAfile secrets/ca-cert -verify_return_error -verify_hostname broker1 </dev/null

docker exec kafka-etapaE /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server broker1:19092 \
  --command-config /etc/kafka/secrets/admin.properties --list
```

**Qué hace cada comando:**
- `openssl s_client` se conecta al listener externo TLS, valida el certificado contra `ca-cert` y comprueba que el hostname sea `broker1`. El resultado correcto termina con `Verify return code: 0 (ok)`.
- `docker exec ... kafka-topics.sh` ejecuta el cliente Kafka dentro de `kafka-etapaE`. Usa `admin.properties` para autenticarse con SCRAM y `--list` para mostrar los topics.

**Resultado esperado:** aparece `dian.facturacion.emitida` en la lista.

### Paso 4 — Verificar rechazo de autenticación

```bash
docker exec kafka-etapaE /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server broker1:19092 \
  --command-config /etc/kafka/secrets/cliente-malo.properties --list
```

**Qué hace:** repite el listado de topics con `cliente-malo.properties`, que contiene una contraseña incorrecta.

**Resultado esperado:** el comando falla por autenticación; ese fallo es intencional. No compartas los perfiles ni sus contraseñas.

## Laboratorio 13 — Autorización de mínimo privilegio

**Objetivo:** comprobar denegación por defecto y aplicar ACL mínimas de escritura, lectura, grupo y cuota.

**Prerrequisitos y archivos:** Compose `docker-compose.etapaE.yml` arriba con el contenedor `kafka-etapaE` saludable. El servicio interno sigue llamándose `broker1`, así que los comandos Kafka usan `broker1:19092`. Se requieren `entorno/secrets/admin.properties`, `cliente.properties`, `analitica.properties`, `scram-credentials.env`, `broker_jaas.conf`, `ca-cert`, `creds`, `truststore.jks` y `broker1.keystore.jks`. El script `acls-minimo-privilegio.sh` es el único script ACL/cuota requerido. Esta variante usa un broker y factor de réplica uno; permite practicar seguridad, no replicación ni alta disponibilidad.

En el repositorio, el script fuente está en `Material/Codigo y entorno de laboratorio/acls-minimo-privilegio.sh`. Antes de continuar, cópialo al directorio `entorno`, donde está el Compose. Desde aquí, ejecuta los pasos del laboratorio dentro de `entorno`:

```bash
cd ~/kafka-dian
cp -n "Material/Codigo y entorno de laboratorio/acls-minimo-privilegio.sh" entorno/acls-minimo-privilegio.sh
cd entorno
test -f acls-minimo-privilegio.sh
```

Si falta el script copiado o cualquiera de los perfiles SCRAM, detente y solicita los archivos; no ejecutes ACL parciales.

### Paso 1 — Comprobar denegación por defecto

Con la Etapa E arriba, pruebe la identidad de servicio sin ACL. Ejecute desde `entorno`:

```bash
cd ~/kafka-dian/entorno
docker exec kafka-etapaE /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server broker1:19092 \
  --command-config /etc/kafka/secrets/cliente.properties \
  --describe --topic dian.facturacion.emitida
```

**Resultado esperado:** Kafka puede responder `Topic 'Optional[dian.facturacion.emitida]' does not exist as expected`. Aunque el mensaje diga que no existe, el administrador ya confirmó que el topic fue creado; Kafka oculta su metadata a `svc-facturacion-prod`, que aún no tiene permiso para describirlo. `--list` también puede omitir topics no autorizados y no mostrar nada. Si el perfil de servicio sí muestra la descripción, detente: ya tiene permiso o se usó otro perfil.

**Aprendizaje:** con `allow.everyone.if.no.acl.found=false`, el acceso se deniega por defecto y los permisos deben ser explícitos.

### Paso 2 — Aplicar ACL y cuota mínimas

El script unificado concede escritura al productor, lectura al principal analítico sobre el topic y el grupo con prefijo `analitica-`, y fija la cuota. Cópialo al broker y ejecútalo como indica su comentario:

```bash
ACL_SCRIPT="acls-minimo-privilegio.sh"
docker cp "$ACL_SCRIPT" kafka-etapaE:/tmp/acls-minimo-privilegio.sh
docker exec -u 0 kafka-etapaE chmod 644 /tmp/acls-minimo-privilegio.sh
docker exec kafka-etapaE env BOOTSTRAP=broker1:19092 bash /tmp/acls-minimo-privilegio.sh
docker exec kafka-etapaE /opt/kafka/bin/kafka-acls.sh \
  --bootstrap-server broker1:19092 \
  --command-config /etc/kafka/secrets/admin.properties \
  --list --topic dian.facturacion.emitida
```

**Resultado:** se aplican los ACL y `consumer_byte_rate=5242880` (5 MiB/s). El script da el permiso de topic y grupo en la misma ejecución, así que esta versión no puede mostrar entre ambos el fallo intencional `GroupAuthorizationException`.

### Paso 3 — Probar escritura y lectura autorizadas

El productor de facturación no tiene permiso de lectura; usa el perfil analítico para consumir:

```bash
printf '{"nit":"900000001","valor":1000}\n' | \
  docker exec -i kafka-etapaE /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server broker1:19092 \
  --producer.config /etc/kafka/secrets/cliente.properties \
  --topic dian.facturacion.emitida

docker exec kafka-etapaE /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server broker1:19092 \
  --consumer.config /etc/kafka/secrets/analitica.properties \
  --group analitica-lab13 --topic dian.facturacion.emitida \
  --from-beginning --max-messages 5
```

**Resultado:** el productor escribe y el consumidor analítico lee con el grupo `analitica-lab13`.

**Aprendizaje:** consumir requiere autorización sobre el topic y sobre el consumer group. El ACL de grupo usa el prefijo `analitica-`; esa convención debe estar gobernada.

### Paso 4 — Verificar cuota y revisar auditoría

El script ya aplicó la cuota. Confírmala y examina las denegaciones del broker:

```bash
docker exec kafka-etapaE /opt/kafka/bin/kafka-configs.sh \
  --bootstrap-server broker1:19092 \
  --command-config /etc/kafka/secrets/admin.properties \
  --describe --entity-type users --entity-name svc-analitica-lectura

cd ~/kafka-dian/entorno
docker compose -f docker-compose.etapaE.yml logs broker1 \
  | grep -i 'denied\|Principal = User' | tail -10 || true
```

Compara la duración de un consumo sintético suficiente antes y después de la cuota, coordinado con el docente. **Resultado:** confirma `consumer_byte_rate=5242880` y registra una línea de auditoría real; si no hay detalle en los logs, anota la limitación.

**Aprendizaje:** `5 MiB/s` es solo un valor de demostración. En producción, define cuotas según capacidad y añade auditoría con detalle suficiente para el SIEM. No inventes logs que no aparecieron.
